# Validation

Automated checks cover protocol frames, variant selection, relay routing, M1/M2 order, preservation of macros/sensor entries, bad responses, slot changes, concurrent edits, failed writes, strict profile imports, and receiver symbol sequencing. Advanced tests cover all five model layouts, field/range validation, separate Pro deadzones, PC-slot restrictions, trigger ranges, preservation of hidden settings, changed-block writes, conflict detection across blocks and button maps, and readback before/after persistence.

Verified October 1, 2026: `npm test` passed 33 protocol/controller/input/auto-connect tests and `npm run build` passed (TypeScript checking and Vite production bundling). All 29 browser scenarios passed, including the receiver losing its Gamepad API entry while HID notifications continue to drive the tester. The browser suite includes a simulated complete receiver session with switching, HID relay, mapping/advanced read/write/save, backups, export of the saved layout, preservation of remap drafts and unedited settings, conflict recovery, and unplug handling. It also covers older models, PC-slot gating, keyboard tab selection, and invalid edits across categories. Gamepad access is stubbed in browser tests to isolate them from attached hardware. The receiver regression uses the observed input-2/output-2 descriptor, ID-zero base-info notifications, and `23` → `22` keymap-write response; it verifies the chooser usage-page filter and checks that unrelated reports cannot satisfy keymap requests. Corrupt map echoes prevent save with either response opcode. Existing input-3 and opcode-23 echo coverage remain.

The UI tests check page and panel overflow, advanced field/card overflow, visible control bounds, button dropdown mapping, and wheel scrolling across eight viewport sizes: 1440×900, 1280×720, 1024×600, 768×1024, 390×844, 360×640, 320×568, and 844×390. All four Advanced categories are checked, including connected/saved states on desktop, mobile, small-phone, and landscape screens. Screenshots of these layouts were inspected using mock devices; a separate geometry review found no overlapping controls.

Joystick tests measure the rendered stick-cap positions on desktop and mobile using simulated standard Gamepad axes. They cover independent left/right movement, selecting another controller, stick-click highlighting, continued mapping-button access, centering when disconnected or using an unverified nonstandard layout, and handling missing/nonfinite/out-of-range axis values.

Controller geometry tests check the entire circular outlines of LS, RS, and XYAB against the SVG shell at each visible viewport size. The stage and controls share the shell's 600×430 coordinates. Trigger tests measure independent analog size changes, partial pressure below the pressed threshold, fixed widths, controller selection, invalid values, and resets for nonstandard/disconnected input. Full-pressure triggers fit above the bumpers on phone and landscape layouts. Desktop, phone, and landscape screenshots were inspected with simulated stick movement and unequal LT/RT pressure.

Hardware status: after the user installed Linux permissions and clicked Connect receiver, the receiver enumerated as `BEITONG A1N3 BFM DONGLE` (`20bc:507f`). The configuration descriptor and live replies confirmed input `2` / output `2`, both with 63-byte payloads. A local TypeScript hidraw adapter exercised the actual `Controller.open()` and `readAdvanced()` implementations successfully: slot 1, all 33 keymap bytes, 21 general-setting bytes, and both 12-byte stick-setting blocks. Base-info notifications carried request ID zero; the other GET replies echoed their request IDs. The initial read-only probe found M2 (left, byte 19) → B and M1 (right, byte 20) → RS click. Raw descriptors and the readback are preserved locally under ignored `.research/`.

The user's subsequent browser Apply attempt reached the mapping write but timed out. A hardware probe reproduced the failure: command `23` returned opcode `22` with the matching request ID and map, which the old dispatcher discarded. After fixing that specific response pair, the actual `Controller.apply({})` completed on hardware: fresh slot/map checks, full map write, matching echo, save `a0` acknowledgement, and matching 33-byte readback. It preserved the mapping present at the start of this probe (M2 → RS click, M1 → B), with baseline/result in `.research/apply-hardware-readback.json`. No button assignments were changed by the probes. The user subsequently confirmed successful browser Apply and corrected physical backkey ordering. Advanced-setting writes and power-cycle persistence remain unverified; the hidraw adapter does not establish those capabilities.

Following the native message dispatcher exposed and corrected an earlier mode-index error: this model enables Xbox routine modes 2 and 3, rather than mode 4. Browser regression coverage stages A → B before connection, keeps Apply disabled through switching, an empty chooser, and denied OS open, preserves the draft, then enables Apply only after a valid map read.

A 45-second Chromium Gamepad API probe found zero live gamepads. No physical mode-switch or mapping-write commands were issued during that probe.

The user later reported that Classic produced left → RS click and right → LS click. The UI positions and preset targets were correct, but a prior edit had incorrectly exchanged the keymap byte labels. Restoring M2 at index 19 and M1 at index 20 fixes that reversal. A regression checks the transmitted preset bytes for every model: Classic left/right = `11`/`12`, Soul = `1`/`12`. The user confirmed that the physical ordering is now correct. A saved map from before this correction is not rewritten automatically.

Configuration input validation: an ordered user test captured M1 (right) as bit 20, M2 (left) as bit 19, left-stick right as X = 0, up as Y = 0, and independent LT/RT pressure up to 255. Raw packets are retained in `.research/browser-hid-1790846080585.jsonl`. The user confirmed that the browser now detects button presses while connected to the configuration HID. Unit tests cover captured packets, byte offsets, both input subtypes, analog values, malformed packets, report/relay filtering, raw-over-mapped priority, and clearing on close. The browser receiver test removes the Gamepad API device after connection and verifies HID-driven button press/release, M1/M2, stick motion, trigger pressure, continued Apply/Advanced behavior, and neutral state after unplugging.

Auto-connect validation uses simulated gamepads and WebHID devices: default-on behavior and manual-button visibility when disabled, recognized presses, the exact 14-symbol sequence, authorized discovery, explicit permission without activation, automatic chooser with activation, blocked/cancelled chooser fallback, automatic reconnect, draft preservation, cancellation during vibration and delayed HID open, and retry only after another press. Unit tests cover discovery filtering/ambiguity and cancellation during discovery. The new automatic flow has not yet been exercised on physical hardware.

Receiver exit tests check both exact `90 <id> 80 03 01` frames, distinct IDs, no map/save changes, closure after a transport failure, and no exit command during ordinary cleanup or non-receiver disconnect. A browser regression verifies that Disconnect remains visible in auto mode, input switches back to a simulated Xbox gamepad, and neither held buttons nor HID connect events immediately reconnect until auto mode is toggled. The user subsequently reported XInput despite a failed-write message; live sysfs inspection confirmed `BEITONG A1N3 XINPUT DONGLE` (`045e:028e`) at port `5-6.4`, USB device 114. The app now observes the transition before classifying a write failure. Browser regressions cover failure on either exit write followed by delayed HID removal/XInput appearance, a genuine failure with BFM remaining present, and removal without a gamepad; the last case does not claim confirmed XInput.

To complete hardware validation:

1. Open the app in desktop Chrome/Edge, wake the controller with a button, and select the receiver in the connection bar.
2. Send Connect receiver; verify the receiver changes to `20bc:507f` and select its configuration interface (observed input/output `2`/`2`, 63-byte payloads; input `3` remains supported when full-size).
3. Read the full map and retain its raw backup. First inspect M1/M2 assignments without changing anything.
4. Apply a reversible button edit, verify matching echo/readback, reconnect the receiver, and confirm output in the tester/game.
5. Power-cycle the controller and reread to establish persistence; restore the original mapping and repeat verification.
6. Read Advanced settings, back up the raw blocks, change one motor strength level, and verify saved readback and power-cycle persistence. Repeat for normal/Pro deadzones, Pro mode in PC slot 1, trigger thresholds/quick triggers, and lighting; restore original values afterward.

If mode switching fails, capture the recent vendor app's USB traffic around entry/exit of configuration mode. Compare packet timing, exact vibration byte values, HID descriptors, relay framing, and firmware identity before expanding compatibility.
